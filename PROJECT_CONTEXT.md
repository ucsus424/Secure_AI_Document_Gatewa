# Secure AI Document Gateway — Project Context

## 1. Задача

На рабочем компьютере доступна внешняя AI-модель Anthropic/Claude, но в неё **нельзя загружать исходные рабочие документы**, потому что они могут содержать чувствительную информацию:

- персональные данные;
- ФИО сотрудников и представителей заказчика;
- названия компаний и клиентов;
- адреса объектов;
- внутренние названия объектов, площадок, узлов;
- IP-адреса;
- IP-планы и подсети;
- hostname;
- MAC-адреса;
- номера телефонов;
- email;
- номера договоров;
- заявки и внутренние идентификаторы;
- логины;
- пароли, токены, ключи и другие секреты.

Идея проекта: использовать **локальную AI-модель** для обнаружения чувствительных данных и создавать обезличенную/псевдонимизированную копию документа, которую уже можно передать Claude.

После обработки Claude чувствительные данные должны локально восстанавливаться.

---

## 2. Главная идея архитектуры

Не нужно строить тяжёлый DLP-комбайн с несколькими AI-моделями.

Для MVP используем:

1. **одну локальную LLM** для смыслового обнаружения чувствительных сущностей;
2. обычный локальный код для:
   - чтения документов;
   - присвоения токенов;
   - замены значений;
   - хранения таблицы соответствий;
   - обратного восстановления.

Схема:

```text
DOCX / XLSX / PPTX / PDF
            |
            v
    Локальный загрузчик
            |
            v
     Gemma 4 12B local
            |
            v
     JSON со списком
   чувствительных сущностей
            |
            v
   Детерминированная замена
            |
      +-----+------+
      |            |
      v            v
 sanitized     mapping.json
 document      LOCAL ONLY
      |
      v
 Claude / Anthropic
      |
      v
 result with placeholders
      |
      v
 локальная обратная замена
      |
      v
 финальный документ
```

---

## 3. Почему не давать LLM самой переписывать документ

Локальная модель должна **находить сущности**, а не выполнять финальную замену текста.

Причины:

- LLM может случайно перефразировать документ;
- может изменить форматирование;
- может дать разную замену одной и той же сущности;
- восстановление через LLM менее надёжно;
- обычная программная замена детерминирована.

Правильный вариант:

```text
Gemma:
"Петров А.В." -> PERSON
"ВРН-Север-17" -> OBJECT
"10.74.16.1/24" -> IP
```

Код:

```text
Петров А.В.       -> ⟦PERSON_001⟧
ВРН-Север-17      -> ⟦OBJECT_001⟧
10.74.16.1/24     -> ⟦IP_001⟧
```

Локальная таблица:

```json
{
  "PERSON_001": "Петров А.В.",
  "OBJECT_001": "ВРН-Север-17",
  "IP_001": "10.74.16.1/24"
}
```

После работы Claude обычный код делает обратную подстановку.

## 4. Терминология

Это не настоящая необратимая анонимизация.

Для проекта правильнее использовать термин:

**обратимая псевдонимизация**.

Исходные значения заменяются стабильными локальными псевдонимами:

```text
Иванов Сергей Петрович -> ⟦PERSON_001⟧
ООО "Альфа Телеком"    -> ⟦COMPANY_001⟧
ВРН-Север-17           -> ⟦OBJECT_001⟧
10.74.16.23             -> ⟦IP_003⟧
```

Одна и та же сущность во всём документе должна получать один и тот же токен.

## 6. Выбранная локальная модель

Основной кандидат:

```text
Gemma 4 12B IT QAT
```

Ollama tag:

```text
gemma4:12b-it-qat
```

Почему выбрана Gemma:

- хорошо понимает русский текст;
- мультимодальная;
- умеет работать с изображениями;
- подходит для OCR/document understanding;
- достаточно компактная QAT-квантизация;
- уже протестирована на M3/16 GB;
- по текущему тесту хорошо распознаёт нужные DLP-сущности.

Важное уточнение:

**сама модель не принимает DOCX/XLSX/PPTX как бинарный Office-файл.**

На уровне модели вход — текст и изображения.

Поэтому приложение должно локально:
- извлечь текст/таблицы;
- извлечь или отрендерить изображения/страницы;
- передать это Gemma.

Для пользователя это всё равно должно выглядеть как:

```text
перетащил .docx/.xlsx/.pptx/.pdf
        ->
получил безопасную копию
```

То есть парсеры являются внутренней технической частью приложения, а не отдельной AI-системой.

## 8. Базовый тест модели

Первый тест:

```text
Ты работаешь как локальная система обнаружения конфиденциальных данных.

Найди в тексте:
- ФИО
- организации
- адреса
- названия объектов
- IP-адреса
- подсети
- hostname
- MAC-адреса
- номера телефонов
- email
- внутренние идентификаторы

Ничего не переписывай. Верни список найденных сущностей с их типами.

Текст:
Начальник участка Иванов Сергей Петрович сообщил об аварии
на объекте Северный по адресу Москва, ул. Ленина, 15.
Маршрутизатор rt-core-01 имеет IP 10.17.31.1/24.
```

Gemma нашла:

```text
Иванов Сергей Петрович -> ФИО
Северный -> название объекта
Москва, ул. Ленина, 15 -> адрес
rt-core-01 -> hostname
10.17.31.1/24 -> IP-адрес / подсеть
```

Вывод:

модель хорошо распознаёт базовые русскоязычные и технические сущности.

Также обнаружился нюанс: нужно жёстко разделять:

```text
10.17.31.1/24 -> IP
10.17.31.0/24 -> SUBNET
```

Это было добавлено в системный prompt следующего теста.

## 9. Текущий DLP prompt

Текущая версия промпта для обнаружения сущностей:

```text
Ты локальная система обнаружения информации, запрещённой для передачи во внешнюю AI-систему.

Найди ВСЕ чувствительные сущности.

Категории:
PERSON — ФИО и части ФИО, позволяющие идентифицировать человека
COMPANY — организации и клиенты
OBJECT — внутренние названия объектов, узлов, площадок
ADDRESS — физические адреса и местоположения
IP — IP-адрес конкретного устройства
SUBNET — адрес сети с CIDR
HOSTNAME — имена серверов, маршрутизаторов и другого оборудования
MAC — MAC-адрес
PHONE
EMAIL
CONTRACT — номера договоров
INTERNAL_ID — внутренние номера, коды объектов, заявки и идентификаторы
LOGIN — логины
SECRET — пароль, токен, ключ или другие секреты

Правила:
1. Не пропускай сущности только потому, что они выглядят техническими.
2. Не изменяй и не пересказывай исходный текст.
3. Для каждого найденного значения верни точную исходную строку.
4. IP вида 10.17.31.1/24 классифицируй как IP, а не SUBNET.
5. SUBNET — это только адрес сети, например 10.17.31.0/24.
6. Если не уверен, всё равно включи сущность и поставь confidence ниже.
7. Верни только JSON-массив без комментариев.

Формат:

[
  {
    "type": "PERSON",
    "value": "Иванов Сергей Петрович",
    "confidence": 0.99
  }
]
```

## 13. mapping / vault

Соответствия должны храниться только локально.

Пример:

```json
{
  "document_id": "uuid",
  "entities": {
    "PERSON_001": "Петров А.В.",
    "OBJECT_001": "ВРН-Север-17",
    "ADDRESS_001": "г. Воронеж, Московский проспект, д. 129",
    "COMPANY_001": "ООО \"Альфа Телеком\"",
    "IP_001": "10.74.16.1/24"
  }
}
```

Никогда не отправлять `mapping.json` во внешнюю AI-модель.

Для MVP допустим обычный локальный JSON.

Для production желательно:
- шифрование;
- отдельный vault;
- автоудаление;
- привязка mapping к конкретному документу/сессии.

## 14. Особенность IP-планов

Простая замена:

```text
10.20.15.1  -> ⟦IP_001⟧
10.20.15.10 -> ⟦IP_002⟧
```

может уничтожить часть полезной информации для Claude.

Например внешний AI перестанет понимать, что два адреса находятся в одной сети.

На первом MVP можно использовать обычные плейсхолдеры.

Но архитектуру желательно сделать так, чтобы позднее появилась возможность:

- генерировать синтетические IP;
- сохранять отношения между сетями;
- сохранять prefix/CIDR structure;
- использовать стабильную псевдонимизацию сетевой топологии.

Это отдельный этап, не блокирующий MVP.

## 15. Форматы документов

Требование:

```text
.docx
.xlsx
.pptx
.pdf
```

### DOCX

Нужно учитывать:

- обычные параграфы;
- таблицы;
- headers;
- footers;
- hyperlinks;
- comments/notes, если доступны;
- embedded images;
- метаданные;
- при необходимости embedded objects.

### XLSX

Нужно учитывать:

- все листы;
- скрытые листы;
- ячейки;
- формулы;
- comments/notes;
- hidden rows/columns;
- named ranges;
- chart labels;
- изображения.

### PPTX

Нужно учитывать:

- текстовые блоки;
- таблицы;
- notes;
- slide titles;
- shapes;
- изображения;
- схемы;
- подписи на картинках.

### PDF

Нужно учитывать:

- текстовый слой;
- сканы;
- таблицы;
- изображения;
- схемы.

Для PDF со сканами страницы нужно передавать Gemma как изображения или выполнять локальный OCR.

## 16. Подход к Office/PDF

Gemma 4 должна быть **единственной AI-моделью**, но не единственным программным компонентом.

Пример:

```text
DOCX
  -> parser
  -> text + images
  -> Gemma

XLSX
  -> parser
  -> sheets/tables + images
  -> Gemma

PPTX
  -> parser
  -> slide text + slide/image rendering
  -> Gemma

PDF
  -> text extraction + page rendering
  -> Gemma
```

Парсер не является "ещё одной AI-моделью".

Это обычный локальный код.

## 19. Модули MVP

### `parser`

Задача:

```text
input file
   ->
normalized document representation
```

Нормализованное представление желательно делать структурированным.

Пример:

```json
{
  "document_type": "docx",
  "blocks": [
    {
      "id": "p_001",
      "type": "paragraph",
      "text": "..."
    },
    {
      "id": "table_001_cell_A1",
      "type": "table_cell",
      "text": "..."
    }
  ],
  "images": []
}
```

Важно сохранять координату/идентификатор источника, чтобы потом менять текст именно в исходном документе.

---

### `detector`

Отправляет локальные фрагменты в Ollama/Gemma.

Вход:

```json
{
  "block_id": "p_001",
  "text": "..."
}
```

Выход:

```json
[
  {
    "type": "PERSON",
    "value": "Петров А.В.",
    "confidence": 0.99
  }
]
```

---

### `anonymizer`

Делает:

```text
real value -> stable placeholder
```

Одна и та же строка в рамках документа:

```text
Петров А.В.
```

всегда превращается в:

```text
⟦PERSON_001⟧
```

---

### `vault`

Хранит:

```text
placeholder -> original value
```

Локально.

---

### `restore`

После Claude:

```text
⟦PERSON_001⟧ -> Петров А.В.
```

Восстановление должно выполняться кодом, а не LLM.

---

### `validator`

## 27. Очень важная проблема восстановления

Если Claude оставляет плейсхолдеры без изменений:

```text
⟦PERSON_001⟧
```

обратная подстановка проста.

Но Claude может:

```text
- удалить placeholder;
- изменить его регистр;
- добавить пробел;
- разбить placeholder форматированием;
- перестроить таблицу;
- создать новый документ.
```

Поэтому системный prompt для Claude должен содержать правило:

```text
Никогда не изменяй токены вида ⟦TYPE_000⟧.
Считай их атомарными идентификаторами.
Копируй их в результат без изменений.
```

Также `restore.py` должен уметь сообщать:

```text
expected placeholders: 48
found placeholders: 46
missing:
- PERSON_003
- OBJECT_007
```

Не выполнять молча "успешное" восстановление, если токены потерялись.

## 35. Итоговое решение на текущий момент

Текущая архитектура:

```text
                    LOCAL

DOCX/XLSX/PPTX/PDF
        |
        v
 parser / renderer
        |
        v
 Gemma 4 12B IT QAT
        |
        v
 sensitive entities JSON
        |
        v
 deterministic pseudonymizer
        |
        +-------------------+
        |                   |
        v                   v
 SAFE document         LOCAL mapping
        |
        |
        +-------- OUTSIDE LOCAL BOUNDARY -------->
        |
        v
   Claude / Anthropic
        |
        <-----------------------------------------
        |
        v
 local restore
        |
        v
 FINAL document
```

Главный принцип:

> **LLM решает, что является чувствительными данными.  
> Код решает, как их заменить и восстановить.**

Это обеспечивает простоту MVP и при этом не делает восстановление зависимым от поведения нейросети.

## 39. Исправление surface-вариантов сущностей

Реальный DOCX показал проблему:

```text
Gemma вернула: ИП Некрылова Г.В.
В документе было также: ИП Некрылова Г.В,,
```

Старая версия делала только exact replace и оставляла второй вариант.

Исправлено:

- для `PERSON`, `COMPANY`, `OBJECT` строятся ограниченные punctuation-flexible surface-варианты;
- варианты получают тот же placeholder;
- дополнительные найденные формы пишутся в `mapping.aliases`;
- Office-заменщик использует и `entities`, и `aliases`;
- добавлены unit tests на TXT и DOCX;
- проблемный файл `МТС - Ленинградская 1 Модернизация.docx` после повторной обработки не содержит фрагмент `Некрылова` в SAFE-тексте.
- alias сохраняется только если он реально был применён при замене, чтобы mapping не засорялся неиспользованными частичными совпадениями.
